## Stagger wrapping pattern (per 02-PATTERNS.md line 353-356)
ChannelButtonRow places the `fade-in-up` + `stagger(3 + i)` on a wrapper `<div>` AROUND each ChannelButton (not on the `<a>` itself). Two reasons:
1. The button has a hover `transform: translateY(-1px)` — if the same element also runs the `fade-in-up` keyframe (which animates `opacity` AND `transform`), the hover translate would collide with the entry animation's final transform state.
2. Cleaner separation: wrapper owns entry animation; button owns hover transitions.

CTAArrowLink, by contrast, ships the `fade-in-up` class on the `<Link>` itself because its hover micro-motion is on a child `<span>` (the arrow), not on the link element.

## CTAArrowLink stagger prop pattern (per 02-PATTERNS.md line 391-395)
The component receives `staggerIndex: number` as a prop. Inline style merges `color: 'var(--color-accent)'` with `...stagger(staggerIndex)` so both ride together. Plan 06's Hero composition passes `staggerIndex={5}` and `staggerIndex={6}`.

## Phase 1 inline-style color convention
Inline `style={{ color: 'var(--color-muted)' }}` for token colors (matches Footer.tsx). Tailwind arbitrary `border-[var(--color-border)]` for border (no inline shorthand). Both work — use inline-style for `color`, arbitrary for `border`/`background`.

## Required Tailwind class invariants (UI-SPEC line 73)
- Forbidden in this plan: `py-2.5`, `gap-1.5`, `translate-x-0.5`, `p-0.5`, `p-1.5`.
- Allowed: integer multiples of 4 for padding/gap/margin.
- `whitespace-nowrap` on ChannelButton — prevents the handle/verb from wrapping to a second line inside a button.

## CTAArrowLink href contract
- Internal routes only (`/about` and `/work`). Plan 04 also rewires Nav.tsx LINKS to point at these routes.
- Use Next.js `<Link>` (not plain `<a>`) — internal routes get client-side prefetch automatically.
- Plan 05 ships the stub pages at `/about` and `/work` so the navigation does not 404.

**Hover-state mechanics** (critical detail):
- The parent `<a>` carries `transition-[border-color,color,transform] duration-200`. On hover, the parent's `:hover` applies `border-[var(--color-accent)]` and the implicit text-color shift on the verb child happens via the cascade: Tailwind doesn't have a direct way to scope a child color change via `hover:` from the parent without arbitrary descendant selectors. Two options:
  - **Option A (preferred — UI-SPEC line 339 contract):** Add `[a:hover_&]:text-[var(--color-text)]` arbitrary descendant selector on the verb span. Tailwind v4 supports this. Verify the syntax against the Tailwind v4 docs.
  - **Option B (fallback):** Apply the `group` class to the parent `<a>` and `group-hover:text-[var(--color-text)]` on the verb span. This is the canonical Tailwind hover-propagation pattern and is already used by CTAArrowLink (Task 3 of this plan) for the arrow micro-motion. Pick this if Option A's arbitrary selector reads brittle.
- Executor picks **Option B** by default (canonical Tailwind pattern, already a project precedent in CTAArrowLink). Add `group` to the parent className. Replace the verb span's color with: `<span className="transition-colors group-hover:text-[var(--color-text)]" style={{ color: 'var(--color-muted)' }}>{verb}</span>`. Note the inline `color: var(--color-muted)` is the rest-state baseline; `group-hover:text-[var(--color-text)]` overrides on hover via the Tailwind utility (utility classes win over inline styles in the cascade ONLY if they use `!important`, which Tailwind v4 utilities do NOT). To make this work cleanly: use `text-[var(--color-muted)]` Tailwind arbitrary instead of inline-style for the rest-state color, so the hover utility class can override it. This breaks the Phase 1 inline-style preference for one specific case — document the deviation in the leading comment ("verb color uses Tailwind arbitrary to allow group-hover override").

export function CTAArrowLink({ href, children, staggerIndex }: CTAArrowLinkProps) {
  return (
    <Link
      href={href}
      className={`group inline-flex items-center gap-2 text-base font-sans hover:underline hover:decoration-1 hover:underline-offset-4 ${fadeInUp}`}
      style={{ color: 'var(--color-accent)', ...stagger(staggerIndex) }}

- Unicode `→` (U+2192) appended as a text child — UI-SPEC line 394 prefers Unicode over lucide `ArrowRight`. The glyph is wrapped in `<span aria-hidden>` so the translation animation applies to the arrow only, not the entire link text.
- The `group` Tailwind class on `<Link>` propagates hover to the arrow span's `group-hover:translate-x-1` (= 4px). Checker revision 2026-05-11 dropped fractional `translate-x-0.5` (2px) to `translate-x-1` (4px) for the on-grid invariant.
- `transition-transform` on the arrow span gives the translate a smooth duration (Tailwind default 150ms; cubic-bezier is the global default per Tailwind v4 — `cubic-bezier(0.4, 0, 0.2, 1)`).
- Underline appears only on `hover:` — at rest the link is a clean accent-colored text (UI-SPEC line 401, D-19 "subtle text-link").
- `fadeInUp` class lives on the `<Link>` itself (not a wrapper div, unlike ChannelButtonRow's pattern). The arrow micro-motion is on a child `<span>` so there's no collision with the entry-animation transform.
- Inline-style merges `color` and `...stagger(staggerIndex)` so both ride together per 02-PATTERNS.md line 399. Plan 06 passes `staggerIndex={5}` for the "More about me" link and `staggerIndex={6}` for "See the work" per CD-03.

**Reduced-motion:** Phase 1's `app/globals.css` lines 54-63 defeats all transitions globally — the arrow translate is automatically off in reduced-motion. No per-component handling needed.

**Per UI-SPEC line 73 invariant:** `gap-2`, `translate-x-1` are integer multiples of 4. No fractional utilities.

**Per FOUND-07 / D-25:** zero `'use client'`. No event handlers.

**Why staggerIndex is a prop rather than computed inside:** the component must be reusable for both CTAs (about + work) with different stagger values. The caller (Plan 06 Hero.tsx) owns the choreography sequence, not the leaf component.

**Edge case — text vs children typing:** the `children` prop is typed as `string` (not `React.ReactNode`). This is intentional — D-19 specifies plain text labels ("More about me", "See the work"). Allowing arbitrary nodes opens the door to nested `<span>` markup that breaks the underline-offset rendering. Lock to `string` for now; revisit in Phase 6 if a future need arises.
