## Spacing Scale

**Inherited from Phase 1 + Phase 2 + Phase 3 + Phase 4 verbatim** (multiples of 4). Phase 5 introduces **zero** new spacing tokens. Modal internals consume tokens from the existing scale per D-17 internal padding spec + locked vertical rhythm.

| Token | Value | Tailwind class | Phase 5 usage |
|-------|-------|----------------|---------------|
| `xs` | 4px | `gap-1` / `mt-1` | Char-counter inline padding-top above (visually-tight metadata under textarea). |
| `sm` | 8px | `gap-2` / `mt-2` | Field label → input gap; char-counter to error-message gap; mailto-link inline arrow gap (matches `<CTAArrowLink>` precedent). |
| `md` | 16px | `gap-4` / `mt-4` | Inter-field gap inside the form (name → email → message); form → mailto-link gap (within idle state); state-message vertical padding. |
| `lg` | 24px | `gap-6` / `p-6` | **Modal internal padding (mobile)** per D-17 (`p-6` = 24px on mobile); heading → form gap. |
| `xl` | 32px | `gap-8` / `md:p-8` | **Modal internal padding (desktop)** per D-17 (`md:p-8` = 32px on tablet+desktop). |
| `2xl` | 48px | (n/a) | Not used in modal composition — reserved. |
| `3xl` | 64px | (n/a) | Not used in modal composition — reserved. |

**Modal external positioning (D-17):**
- `mx-4` on mobile (16px horizontal page margin between dialog edge and viewport edge — prevents the dialog from butting against the screen edge on small phones).
- `max-w-md` (28rem / 448px) — the dialog's max-width on all viewports.
- Centered horizontally + vertically by the browser's native `<dialog>` `showModal()` top-layer behavior. NO custom transform centering needed.

**Modal internal padding (D-17 — locked):**
- Mobile: `p-6` (24px all sides).
- Tablet+desktop: `md:p-8` (32px all sides).

**Modal max-height + scroll behavior (NEW — discretion-driven, planner-honored):**
- `max-h-[calc(100vh-2rem)]` on the `<dialog>` element so the modal never exceeds the viewport (with 1rem top + bottom breathing room from the browser's native centering).
- Internal `<form>` element gets `overflow-y-auto` so a 1000-char message at full size doesn't push the submit button off-screen on a small phone.
- On a typical 375px-wide phone with all 3 fields filled to ~80% capacity, the modal height lands ~640-680px → comfortably fits without scroll. The `overflow-y-auto` is belt-and-suspenders for edge cases (small phones with zoom enabled, very long error messages).

**Vertical rhythm INSIDE the dialog (top-to-bottom — locked):**

| From → To | Gap (px) | Tailwind class | Rationale |
|-----------|----------|----------------|-----------|
| Heading → first field (Name label) | 24px | `mt-6` | Heading is the section anchor; field group is the action. Comfortable separation matches Phase 4's status-badge → title rhythm at the same `mt-6` proportion. |
| Field group internal (label → input) | 8px | `mt-2` | Tight pair — label is the input's identifier. |
| Field group internal (input → next-label) | 16px | `mt-4` | Each name/email/message field group is its own unit — 16px between groups matches Phase 4's status → title 16px proportion. |
| Textarea → char counter | 4px | `mt-1` | Tight metadata pair — counter "belongs to" the textarea. |
| Form (last field block) → Send button | 24px | `mt-6` | Send is the action; the gap signals "you've finished filling, now act." |
| Send button → mailto fallback | 16px | `mt-4` | Fallback is form-adjacent metadata, not a primary CTA. Closer than the heading→form gap. |
| State message ("Sending…" / success / error) → mailto fallback | 16px | `mt-4` | Same proportion as Send → mailto in idle state — keeps the modal's visual rhythm stable across state transitions. |

**Field-internal padding** (input + textarea):
- `px-3 py-2` (12px horizontal, 8px vertical) — on-grid (multiples of 4 — 12 = 3×4, 8 = 2×4). Matches Phase 2 ChannelButton's `px-4 py-3` proportion scaled down for inline form fields. NOT `px-4` (would feel chunky inside a 384px-content-width modal). NOT `p-2` symmetric (vertical-tight reads cramped for input/textarea content).

**Send button + mailto link sizing:**
- Send button: same `px-4 py-3` proportion as Phase 2 ChannelButton (D-12 ChannelButton precedent — same hairline-tile button family per D-09 inheritance). The button is right-aligned at the bottom-right of the form (NOT full-width — full-width would feel "app-y" and break the editorial-tile language).
- Mailto link: text-link with arrow glyph, no padding/border — matches Phase 2 `<CTAArrowLink>` pattern verbatim per D-15 wording.

**Exceptions** (Phase-5-specific): **None.** All spacers are multiples of 4. No `0.5` / `2.5` / `3.5` fractional Tailwind utilities used in any component contract. (`mt-1` = 4px and `w-1.5` = 6px are explicitly on-grid in this project's Tailwind v4 setup — see Phase 2 + 4 inheritance.)

**Send button color treatment (D-09 — locked):**
- Rest state: `color: var(--color-accent); background: transparent; border: 1px solid var(--color-border);`
- Hover state: `border-color: var(--color-accent); color: var(--color-accent);` (color unchanged; border transitions per the same Phase 2 + 4 transition-property discipline below)
- Focus-visible: Phase 1 global ring (2px solid `--color-accent`, 2px offset)
- Disabled state (during submitting): `opacity: 0.6; cursor: not-allowed; pointer-events: none;` — desaturates the accent, communicates "wait."

**Input + textarea color treatment (locked):**
- Rest state: `color: var(--color-text); background: transparent; border: 1px solid var(--color-border);`
- Placeholder: `color: var(--color-muted);` (set via `::placeholder` selector on each input/textarea)
- Focus state (focus-visible): border transitions to `var(--color-accent)`; Phase 1 global focus ring applies (2px outline accent + 2px offset). The 1px border + 2px outline + 2px offset gives a clear focus indicator without doubling-up visually.
- Disabled state (during submitting): `opacity: 0.6; cursor: not-allowed;` — same treatment as Send button for state consistency.
- Error state (after submit-attempt with invalid input): border transitions to `var(--color-accent)` (same as focus — the inline error message text below the field carries the meaning per A11Y-05; color is never the only indicator).

**Destructive color:** Phase 5 has zero destructive actions. The form-clear that happens when the modal closes is reversible (browser autofill recovery preserves typed content in many browsers). No destructive token introduced. (Inherited from Phases 1–4: still none defined for v1.)

## State Visual Treatments (CTCT-03 — locked verbatim copy + aria-live announcement contract)

The modal renders **exactly four** states. Each state has both a **visible UI treatment** AND a **screen-reader-announced treatment** via `aria-live` regions per CTCT-03 binding. Copy is locked verbatim in D-08..D-12.

### State 1: Idle (default — modal just opened, user has not submitted)

**Visible treatment:**
- Heading "Get in touch" rendered at top.
- 3 fields rendered (name + email + message + counter).
- Send button at bottom-right of form, label "Send message", enabled.
- Mailto fallback link below Send button: "Or just email me directly →".
- `aria-live` polite region: empty (no announcement).

**Screen-reader treatment:** Dialog opens → focus moves to first focusable element (per Tab Order section below) → screen reader announces dialog heading via `aria-labelledby` ("Get in touch dialog"). No additional announcement.

### State 2: Submitting (user clicked Send, request in flight)

**Visible treatment:**
- All 3 fields disabled (opacity 0.6, cursor not-allowed) — typed content remains visible per D-12.
- Send button label changes to "Sending…" per D-09 + D-12 verbatim.
- Send button disabled (opacity 0.6, cursor not-allowed, pointer-events none).
- Form gets `aria-busy="true"` per D-12.
- Mailto fallback link remains visible + interactive (a Formspree-DoS-during-submit doesn't block the visitor's defection-to-email).
- NO spinner glyph per D-12 explicit — the label change + disabled state communicates clearly.

**Screen-reader treatment:** `aria-live="polite"` region announces "Sending your message." (Claude's discretion in CONTEXT.md anchored to warm-personal first-person voice; matches the editorial register.)

### State 3: Success (Formspree returned a successful response)

**Visible treatment:**
- **Form replaces with success message** per D-10. The `<form>` element is conditionally not-rendered; in its place sits a `<div>` containing the success copy + "Send another →" reset link.
- Success copy rendered at 16px Geist Sans 400 in `--color-text`: **"Thanks — I'll get back to you within a day or two."** verbatim per D-10.
- "Send another →" link below success copy, styled per `<CTAArrowLink>` pattern (accent color, group-hover arrow translate) — clicking resets all form state to idle.
- Heading "Get in touch" remains at top (gives the success state a stable anchor matching the idle-state visual structure).
- Mailto fallback link remains visible below the success block (a visitor who got a successful submit may STILL want the email link for follow-up — it's a low-cost extra surface).

**Screen-reader treatment:** `aria-live="polite"` region updates to: "Message sent. Thanks." (Claude's discretion — matches D-10's warm-personal register, slightly compressed for screen-reader brevity.)

### State 4: Error (Formspree returned an error response — network, 4xx, 5xx)

**Visible treatment:**
- **Error message renders ABOVE the form** (form remains visible — typed content survives). The `<div role="alert">` containing the error copy sits at top of form area, just below the heading.
- Error copy rendered at 16px Geist Sans 400 in `--color-text`: **"Something went wrong sending that. Try the email link below."** verbatim per D-11.
- Heading "Get in touch" remains at top.
- 3 fields remain populated + enabled (visitor can retry by editing + resubmitting, OR defect to mailto per the error copy's explicit pointer).
- Send button label returns to "Send message" + enabled (no auto-retry, no auto-block — visitor controls the retry).
- Mailto fallback link remains visible + interactive at the bottom — explicitly referenced in the error copy ("Try the email link below").

**Screen-reader treatment:** `aria-live="assertive"` region announces: "Something went wrong sending your message. Try the email link below." (matches D-11 verbatim with "your" added for screen-reader naturalness.)

**State transitions:**
- Idle → Submitting: triggered by Send button click + form passing client-validation + honeypot empty + min-time-to-submit elapsed.
- Submitting → Success: triggered by Formspree returning 200 OK.
- Submitting → Error: triggered by Formspree returning non-2xx OR network failure.
- Success → Idle: triggered by "Send another →" click (resets form state, clears all field values).
- Error → Idle: triggered by user editing any field (clears the error message, returns to idle visual without resetting field values) OR by user clicking Send again.

**Honeypot + min-time-to-submit silent rejection:**
- Honeypot non-empty (D-13): submit handler returns success-shaped state immediately (looks like Idle → Success transition to the bot, but NO Formspree call is made + NO email sent).
- Min-time-to-submit < 1500ms (D-14): same silent-success treatment.
- Both rejections are visually + behaviorally indistinguishable from a real success to the user/bot — no error feedback, no rate-limit message. This is the design.

## Modal Entrance Motion (D-16 — locked)

**Entrance animation:**
- The `<dialog>` element fades in from `opacity: 0` to `opacity: 1` over **200-240ms** with `cubic-bezier(0.2, 0, 0, 1)` easing (matches Phase 1's `fade-in-up` keyframe easing).
- The `dialog::backdrop` fades in over **150ms** with the same easing (per D-16 explicit — backdrop ramps slightly faster than dialog content).
- NO transform animation (no slide-in, no scale-in) — pure opacity fade per the editorial-restrained motion contract.

**Implementation pattern** (planner discretion — recommended approach):

Option A — `@starting-style` (modern CSS, Chrome/Safari/Firefox 117+ support):
```css
dialog[open] {
  opacity: 1;
  transition: opacity 240ms cubic-bezier(0.2, 0, 0, 1);
}
@starting-style {
  dialog[open] {
    opacity: 0;
  }
}
dialog::backdrop {
  background-color: rgba(10, 10, 10, 0.6);
  backdrop-filter: blur(2px);
  opacity: 1;
  transition: opacity 150ms cubic-bezier(0.2, 0, 0, 1);
}
@starting-style {
  dialog::backdrop {
    opacity: 0;
  }
}
```

Option B — `@keyframes` + `dialog[open]` selector (broader browser support):
```css
@keyframes modal-fade-in {
  from { opacity: 0; }
  to   { opacity: 1; }
}
dialog[open] {
  animation: modal-fade-in 240ms cubic-bezier(0.2, 0, 0, 1) both;
}
dialog[open]::backdrop {
  animation: modal-fade-in 150ms cubic-bezier(0.2, 0, 0, 1) both;
  background-color: rgba(10, 10, 10, 0.6);
  backdrop-filter: blur(2px);
}
```

**Reduced-motion override:** The global `@media (prefers-reduced-motion: reduce)` rule in `app/globals.css` lines 54-63 already sets `animation-duration: 0.01ms !important; transition-duration: 0.01ms !important` for all elements. Both Option A (transition) and Option B (animation) are defeated automatically — backdrop appears instantly with same dim color, dialog appears instantly with `opacity: 1`. NO additional reduced-motion CSS rule needed in Phase 5. Verified via Phase 1 contract inheritance.

**No per-element stagger inside the modal** — per CONTEXT.md Claude's Discretion: "Stagger choreography for the modal contents on open — likely none (the modal itself fades in; per-element stagger inside a 200ms modal entrance would feel chaotic)." Modal contents render at full opacity from frame 1 of the 240ms fade-in. The dialog as a whole is the animated unit.

**`fadeInUp` reuse decision (D-16 anchor):** The Phase 1 `fade-in-up` keyframe (`from { opacity: 0; transform: translateY(8px); } to { opacity: 1; transform: translateY(0); }`) translates the element up by 8px during fade-in. **Phase 5 does NOT reuse `fade-in-up` for the modal entrance** — the 8px translateY would visually conflict with the browser-centered dialog (the 8px shift would appear as a "jump" since the dialog is positioned by `<dialog>` `showModal()` top-layer rules, not by margins). Use the new `modal-fade-in` keyframe (Option A or B above) which is opacity-only.

The single `href` swap covers both surfaces — mobile-hamburger users get the same `Contact` label that opens the modal via the same hash mechanism.

**Trigger architecture (D-06 strong recommendation — hash-based):**

The recommended pattern keeps Nav.tsx + CTAArrowLink.tsx as Server Components (no client wrappers, preserving the FOUND-07 single-island invariant most cleanly):

1. ContactModal client island mounts in `app/layout.tsx` (or thin wrapper) so it's available globally.
2. Nav `Contact` link `href="#contact"` + /about CTA `href="#contact"`.
3. ContactModal client island uses `useEffect` to:
   - On mount: check `if (location.hash === '#contact') dialogRef.current?.showModal();`
   - Subscribe to `window.addEventListener('hashchange', ...)`: same check.
4. ContactModal close handler clears the hash: `location.hash = '';` (or `history.replaceState(null, '', location.pathname + location.search)` if planner wants to avoid the implicit scroll-to-top behavior of clearing hash).

**URL bookmarkability win:** `braehods.com/about#contact` opens the dialog directly on page load. `braehods.com/#contact` works from home. Browser-back-button closes the modal naturally (back navigation un-sets the hash, which the hashchange listener catches → closes the dialog).

**Planner alternative (D-06 fallback):** If hash-based architecture fails feasibility check (e.g., Next.js Link's client-side navigation behavior conflicts with the hashchange listener), the fallback is a small client-wrapper component `<ContactTrigger>` exposing an `openContact()` callback that wraps the existing Nav links + /about CTA. **This adds a 2nd `'use client'` directive**, breaking the FOUND-07 single-island contract. **Document the deviation explicitly in Phase 5 SUMMARY** if exercised. Default expectation per D-06 strong recommendation: hash-based works; no client wrapper needed.

## Honeypot + Min-Time-to-Submit Visual Contract (D-13 + D-14 — bot defense, invisible by design)

**Honeypot field (D-13 — locked):**
- Field name: `company` (NOT `_gotcha` per CTCT-04 explicit exclusion — Formspree's documented honeypot name is well-known to bots).
- HTML: `<input type="text" name="company" tabindex={-1} autoComplete="off" />`
- Wrapper: `<div className="absolute -left-[9999px] opacity-0 pointer-events-none" aria-hidden="true">`
- Visual treatment: **Invisible to humans** (off-screen position + zero opacity + pointer-events disabled). Skipped by screen readers (`aria-hidden="true"` on wrapper). Skipped by keyboard tab (`tabindex={-1}`).
- Bot detection: submit handler checks `if (formData.get('company')) { return silentSuccess(); }` — bots that DOM-enumerate + fill all visible-name-attribute inputs trip this. Real users never see or interact with it.

**Min-time-to-submit (D-14 — locked):**
- Threshold: **1500ms** (1.5 seconds) — below human read-form-and-fill speed; above bot DOM-mount-and-submit speed.
- Implementation: `const mountTime = useState(() => Date.now())[0];` (lazy init — runs once on mount). Submit handler checks `if (Date.now() - mountTime < 1500) { return silentSuccess(); }`.
- Visual treatment: **None** — entirely invisible. Submission within 1500ms returns success-shaped UI state (Idle → Success transition) but NO Formspree call. Bot sees "success," real visitor never trips it because filling 3 fields takes >1.5s.

**Silent success behavior (locked):** Both honeypot trip + min-time trip return the success state UI (the form replaces with the "Thanks — I'll get back to you within a day or two." message + "Send another →" reset). This makes the bot defense indistinguishable from a real success — no error feedback that bots can train against, no rate-limit warning that exposes the defense mechanism.

**Out of scope (per CONTEXT.md `<deferred>`):** reCAPTCHA, hCaptcha, Cloudflare Turnstile — explicit reject per REQUIREMENTS.md "Out of Scope" + memory `feedback_avoid_paid_tools.md`. Honeypot + min-time-to-submit are the v1 bot-defense tools; Cloudflare Turnstile is the documented future migration target IF spam volume warrants.
