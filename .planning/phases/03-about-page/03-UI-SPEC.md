## Typography

**Type ramp is inherited entirely.** Phase 3 ships **zero new typography roles**. The page renders prose using Phase 2's `Body / 16px / Geist Sans / 400 / line-height 1.5` role — exactly the role the home positioning subhead **base** is built on (Phase 2 uses the larger 18px `text-lg` variant for the positioning subhead specifically; /about uses the regular 16px `text-base` for prose).

| Role | Size (px / rem) | Font | Weight | Line height | Tailwind class | Phase 3 use |
|------|-----------------|------|--------|-------------|----------------|-------------|
| **Body / bio prose** | 16px / 1rem | Geist Sans | 400 | 1.5 (`leading-relaxed` = 1.625 acceptable for prose-density blocks; planner picks 1.5 vs 1.625 — see "Line-height resolution" below) | `text-base font-sans leading-relaxed` | All bio paragraphs. Color `var(--color-text)` so the prose lands — this is the page's primary content. |
| **CTA arrow-link label** | 16px / 1rem | Geist Sans | 400 | 1.5 | `text-base font-sans` | Inherited from `<CTAArrowLink>` (Phase 2 D-19) — accent text color. Reuse the existing component. |

**Line-height resolution:** Bio paragraphs use `leading-relaxed` (Tailwind utility = 1.625) rather than the home positioning subhead's `leading-relaxed` (same class, same value). Rationale: prose blocks at 16px with ~44ch line width read more comfortably at 1.5–1.65 than at the default 1.5. The Tailwind v4 `leading-relaxed` shorthand (1.625) sits within the editorial range and stays Phase-1-compatible (no new token). Two-paragraph and three-paragraph splits both pass at this line-height.

**Weight inventory:** **Exactly one weight** on the new `/about` content — Geist Sans 400 (regular). No bold, no medium, no italics. (Note: the inherited Nav + Footer chrome carries the existing weight inventory; this row counts only Phase-3-added content.) Phase 1's 2-weight contract holds project-wide: Fraunces 700 (display, **not used on /about**) + Geist Sans 400.

**Hard rules** (inherited from Phase 1 / Pitfall 3 — restated for executor):
- **No Fraunces below 40px** — /about uses no Fraunces at all. The page-level container provides no `<h1>`; the bio opens as prose. (Compare: the home page's single Fraunces `<h1>Braeden</h1>` is the brand wordmark; /about does not need to restate the wordmark since the Nav already carries the monogram + name.)
- **No italic Fraunces** — moot on this page since Fraunces isn't used.
- `font-feature-settings: 'kern', 'liga'; text-rendering: optimizeLegibility;` globally applied (Phase 1 `body` rule).

**LCP candidate rule (inherited from Phase 2 D-24):**
- The `<HeroPhoto>` on `/about` is the designated LCP element here too (the largest image above the fold).
- The photo carries **no animation** — same contract as on `/`.

## Bio Prose Contract

**This section locks the *contract* the prose must satisfy. It does NOT specify the literal sentences.** Per `03-CONTEXT.md` D-01, Claude drafts the first-pass prose at execute-phase time and the user edits in-place before commit.

### Length contract (D-06, ABOUT-04)

| Metric | Target | Maximum |
|--------|--------|---------|
| Total word count | 150–250 words | 300 words hard ceiling |
| Read time | ~60 seconds (ABOUT-04 — average reader at 200 wpm reads 200 words in 60s; the target band lands well inside 60s) | n/a |
| Paragraph count | 2 OR 3 paragraphs (planner's call; both pass D-06) | 3 hard ceiling |
| Sentences per paragraph | ≤4 (D-06) | 5 hard ceiling |
| Lines per paragraph on desktop at `max-w-[44ch]` | ≤4 visual lines (D-06 derivative) | 5 hard ceiling |

**Verification math:**
- At 200 words / 60s read target: a 200-word bio reads in 60 seconds for an average reader. The 150–250 word band gives ±25% slack.
- At ~44 characters per line and ~5 characters per word average (Geist Sans English prose typical), a 44-char line holds ~8–9 words. A 250-word bio at 9 words/line = ~28 lines = ~7 visual lines per paragraph if 4 paragraphs, ~9 if 3 paragraphs, ~14 if 2 paragraphs. **3-paragraph split (≤4 sentences each) hits the "scannable" goal of ABOUT-04 best;** 2-paragraph is acceptable if each paragraph stays ≤4 sentences (which at 250-word ceiling means denser paragraphs with shorter sentences — fine for the warm-and-personal voice).

### Voice contract (D-02, ABOUT-01)

| Property | Value |
|----------|-------|
| Pronoun | First-person — "Hi, I'm Braeden — I…" / "I'm currently…" / "I'm open to…" |
| Register | Warm + personal, conversational. Hints at curiosity beyond the resume. |
| Excluded register | Dry / minimal third-person (brittanychiang.com terseness — too cold for this site's mood) |
| Excluded register | Earnest / why-I-build (explicit user exclusion per D-04 — no origin-story or "why I love building" narrative paragraph) |
| Style anchor | The hero positioning line (`Business student and entrepreneur in LA, building things and running a small content brand.`) sets the desktop-positioning voice; /about extends it into longer prose without contradicting it. |

### Cliché-ban contract (D-05, ABOUT-01)

The bio prose **MUST NOT** contain any of these template phrases (case-insensitive, exact-or-near-match):

| Banned phrase | Why banned |
|---------------|------------|
| `passionate developer` | ABOUT-01 explicit |
| `I love to learn` / `lifelong learner` | Recruiter-resume cliché |
| `I am driven by` / `driven to` | LinkedIn-bio cliché |
| `innovative` (as a self-descriptor) | Empty signal |
| `cutting-edge` | Same |
| `I am a [role] with experience in [list]` | Resume-objective template |
| `wear many hats` | Recruiter-resume cliché |
| `results-oriented` / `outcome-driven` | Same |
| Any emoji | Voice guardrail (Phase 1 chrome rule) |
| Any exclamation point | Voice guardrail (Phase 2 inherited — "editorial restraint, no exclamation points anywhere in hero copy") |

**Spec-level enforceable:** A Playwright spec asserting `expect(aboutText).not.toMatch(/passionate|I love to learn|driven by|innovative|cutting.edge|lifelong learner|wear many hats|results.oriented|outcome.driven/i)` is the minimum cliché-scrub assertion. The plan must include this assertion.

### Content-bucket contract (D-03, D-04, D-18, D-19)

The bio MUST cover exactly these three buckets, in the order specified, woven into the 2–3 paragraph structure:

| Bucket | Required content | Where it lives | Source |
|--------|------------------|----------------|--------|
| **1. Who + where + studying** | Name introduction + LA location + business-student framing | Opening sentence of paragraph 1 — anchors identity within the first ~15 words | D-03 bullet 1, D-19 (location inline, NOT a dedicated `Location:` line) |
| **2. Current focus** | What user is building NOW: CapitolLens (Form 4 insider-buy signals, paper-trading), two-channel YT Shorts brand (POV stories + meme reactions), dev tools (GSD / shorts-factory / meme-dashboard / reel-research-agent — exact selection at planner discretion; 2–3 named projects max to stay under word ceiling) | Paragraph 2 (or end of paragraph 1 if 2-paragraph split) — replaces the resume-style "Current focus:" labeled field per D-18 | D-03 bullet 2, D-18 (woven into prose, NOT a labeled metadata strip; NOT a separate `<CurrentlyLine>` block — that would duplicate the home page signal) |
| **3. Open-to invitation** | Explicit "open to / interested in / curious about" phrasing that lands as a low-friction conversion signal. Examples within voice: "open to trading-desk internships, content collabs, or just a chat about what's working in AI-finance." Concrete, specific, not "always looking to chat." | Final paragraph — sits immediately before the `<CTAArrowLink>` so it primes the click. | D-03 bullet 3 |

**Bucket NOT included (D-04 explicit exclusion):**
- **Origin / "why I build"** — no biographical backstory paragraph. The bio answers "what" and "what next," not "why."

**Photo wrapper alt text:** Same as home — `alt="Braeden Hodson"`. NOT `"Headshot of Braeden Hodson"` (over-described per `03-CONTEXT.md` `<specifics>`). NOT `"Picture of myself on /about"`. The same string the home hero uses, so any screen-reader user navigating between `/` and `/about` hears the same person identifier.

**Optional inline mentions** (within the voice + cliché ban):
- Instagram handle: if the open-to bucket mentions DMs / Instagram, render the handle as plain text body color (`@braehods`), NOT as an accent-colored link, NOT as an inline social icon. Phrasing should mirror the IG CTA contract from memory `feedback_reel_cta_dm_format.md`: "DM me @braehods" rather than "follow me on Instagram."
- GitHub: if mentioned at all, plain text — the Footer source link already covers GH discoverability. Better to leave GH out of the bio prose entirely; the dev-tools bucket implies the work.

### Cliché-scrub gate (binding — execute time)

Before the first commit of `app/about/page.tsx` with real prose, the executor MUST:
1. Read the drafted bio aloud (or have user read it aloud — user is the final arbiter per D-01).
2. Run the cliché-ban regex assertion locally.
3. Verify word count is 150–250 (`wc -w` on the prose extracted from the JSX, or eyeball).
4. Verify the three required buckets are present in order.
5. Verify no exclamation points and no emoji.

If any check fails: revise prose, do not commit. Document the revision in execute summary.

## Motion Choreography

Phase 3 extends the Phase 2 motion contract by one route. The animation budget is **smaller** than the home hero — fewer elements stagger.

### Stagger sequence on `/about` page load

| # | Element | Animation | Delay (`stagger(i)`) | Total time after load |
|---|---------|-----------|----------------------|------------------------|
| — | Photo (HeroPhoto wrapper) | **None** (LCP element, D-24 inherited) | — | Renders at first paint |
| 1 | Bio paragraph 1 | `fade-in-up` 400ms | `stagger(1)` = 80ms | ~480ms |
| 2 | Bio paragraph 2 | `fade-in-up` 400ms | `stagger(2)` = 160ms | ~560ms |
| 3 | Bio paragraph 3 (if 3-paragraph split) | `fade-in-up` 400ms | `stagger(3)` = 240ms | ~640ms |
| 3 OR 4 | CTA `Get in touch →` | `fade-in-up` 400ms (component default) | `stagger(3)` if 2-paragraph bio, `stagger(4)` if 3-paragraph bio | ~640ms OR ~720ms |

**Implementation pattern:**

```tsx
import { fadeInUp, stagger } from '@/lib/motion';
import { HeroPhoto } from '@/components/home/HeroPhoto';
import { CTAArrowLink } from '@/components/home/CTAArrowLink';

export default function AboutPage() {
  return (
    <section data-test="about-section" className="py-8 md:py-12">
      <div
        data-test="about-flex"
        className="flex flex-col-reverse gap-8 md:flex-row md:items-center md:gap-16"
      >
        <div className="flex flex-col items-start">
          <p className={`max-w-[44ch] font-sans text-base leading-relaxed ${fadeInUp}`}
             style={{ color: 'var(--color-text)', ...stagger(1) }}>
            {/* bio paragraph 1 — bucket 1: who + where + studying */}
          </p>
          <p className={`mt-4 max-w-[44ch] font-sans text-base leading-relaxed ${fadeInUp}`}
             style={{ color: 'var(--color-text)', ...stagger(2) }}>
            {/* bio paragraph 2 — bucket 2: current focus */}
          </p>
          {/* Optional paragraph 3 — bucket 3: open-to invitation. If 2-paragraph split, weave bucket 3 into end of paragraph 2. */}
          <div className="mt-6">
            <CTAArrowLink href="/" staggerIndex={3 /* or 4 if 3-paragraph */}>
              Get in touch
            </CTAArrowLink>
          </div>
        </div>
        <HeroPhoto />
      </div>
    </section>
  );
}
```

**Notes:**
- **Photo does NOT animate** — D-24 inherited. The photo carries the view-transition seam, which is browser-driven motion, not CSS keyframe motion. The two are separate concerns.
- The `fade-in-up` keyframe duration (400ms) is the Phase 1 baseline; do not override.
- Stagger increments are 80ms (the Phase 1 `stagger(i)` formula = `i * 80ms`).
- The CTA's `staggerIndex` prop is owned by the caller (the page) per Phase 2's CTAArrowLink contract — pass it explicitly.

### Reduced motion

Phase 1's global override defeats all `fade-in-up` keyframe duration and the CTA arrow's `transition-transform`. View-transition cross-fades also defeated by browser-level respect of `prefers-reduced-motion`. **Verify on deployed preview** that toggling DevTools "Emulate prefers-reduced-motion: reduce" renders the page instantly with no fade and no transition shimmer when navigating from `/` to `/about`.
